# Score specification

First and foremost, Score is a Specification.

The Score Specification is what Developers will use to describe in a YAML file what their workload needs. Eventually someone later will deploy it somewhere with a Score implementation.

## Simple Score file

The simplest Score file that you can have is:
```yaml
apiVersion: score.dev/v1b1
metadata:
  name: my-workload
containers:
  my-container:
    image: .
```

This is defining that the workload `my-workload` has one container `my-container`, and at this stage the container image name is not known (`.`) and will be supplied later in the CI/CD workflow.

_Note: it's not a Kubernetes Custom Resource._

## More complex Score file

Now here is a more realistic workload definition, a public service talking to a PostgreSQL database (:fileLink[score.yaml]{path="score.yaml"}):
```yaml save-as=score.yaml
apiVersion: score.dev/v1b1
metadata:
  name: hello-world
  annotations:
    tags: "nodejs,http,website,javascript"
containers:
  hello-world:
    image: .
    variables:
      PORT: "3000"
      MESSAGE: "Hello, World!"
      DB_DATABASE: ${resources.db.name}
      DB_USER: ${resources.db.username}
      DB_PASSWORD: ${resources.db.password}
      DB_HOST: ${resources.db.host}
      DB_PORT: ${resources.db.port}
resources:
  db:
    type: postgres
  dns:
    type: dns
  route:
    type: route
    params:
      host: ${resources.dns.host}
      path: /
      port: 8080
service:
  ports:
    www:
      port: 8080
      targetPort: 3000
```

Let's break it down:

- **`metadata`**: the name of the Workload (`hello-world`) and optional `annotations`.
- **`containers`**: the container(s) of the Workload. Here, one container `hello-world` with its environment `variables`. The image is still `.`, it will be provided at deployment time.
- **`resources`**: the dependencies of the Workload. The Developer only asks for a `type` (`postgres`, `dns`, `route`), there is nothing here about which PostgreSQL version, which Docker image, which Kubernetes `StatefulSet`, etc.
- **`service`**: the ports the Workload exposes to others (port `8080` forwarding to the container port `3000`).

## Placeholders: the glue between Workloads and Resources

Notice the `${resources.db.host}` syntax: this is a **placeholder**. Each resource, once provisioned, exposes **outputs** (for a `postgres` resource: `host`, `port`, `name`, `username`, `password`, ...). Placeholders let the Workload consume these outputs without knowing their actual values.

Resources can also consume the outputs of other resources: the `route` resource uses `${resources.dns.host}` as its `host` parameter.

> 💡 The Developer never writes a hostname, a port or a password. These values are generated by the Score implementation and its resource provisioners, you will see them in action in the next sections.

## Validation and autocompletion in your IDE

The Score specification is published as a [JSON schema](https://github.com/score-spec/spec/blob/main/score-v1b1.json). IDEs can use it to validate your Score files and to autocomplete them while you type.

The VS Code of this Labspace is already configured for that: the [YAML extension](https://open-vsx.org/extension/redhat/vscode-yaml) is installed, and the Score JSON schema is mapped to the `score.yaml` and `*.score.yaml` files in the :fileLink[`.vscode/settings.json`]{path=".vscode/settings.json"} file:
```json
{
  "yaml.schemas": {
    "https://raw.githubusercontent.com/score-spec/spec/main/score-v1b1.json": ["score.yaml", "*.score.yaml"]
  }
}
```

Try it out! Save this Score file, it contains two mistakes:
```yaml save-as=my-workload.score.yaml
apiVersion: score.dev/v1b1
metadata:
  name: my-workload
containers:
  my-container:
    image: nginx
    variabls:
      MESSAGE: "Hello, World!"
service:
  ports:
    www:
      port: "eighty"
```

Open the :fileLink[`my-workload.score.yaml`]{path="my-workload.score.yaml"} file in VS Code:

- `variabls` is underlined: this property is not allowed in a container. Fix it to `variables`.
- `"eighty"` is underlined: the `port` of a service must be a number. Fix it to `80`.
- Hover any field (like `image` or `service`) to see its description from the Score specification.
- On a new line under `my-container`, press `Ctrl+Space` to see the list of supported fields (`command`, `files`, `livenessProbe`, `resources`, ...).

_Note: To get the same experience on your own machine, follow the [IDE linter setup guide](https://docs.score.dev/docs/score-specification/ide-linter-autocomplete/)._
